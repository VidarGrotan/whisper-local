# Windows Runtime Reliability

**Status:** Proposed for local installation review  
**Date:** 2026-09-29

## Problem

The current installation has two independently observed failure modes:

1. Windows can retain the expected `HKCU\...\Run` value but fail to invoke it after login. The existing checker reports success because it validates only the registry text. On 2026-09-29, ordinary startup applications launched after Explorer, but Whisper Local produced no new PID or initialization log until the same VBS launcher was invoked manually.
2. A long-running process can survive Modern Standby while its continuous PortAudio callback stops. The tray process and hotkeys remain alive, so process-only monitoring cannot detect the loss of microphone audio.

The installation therefore needs observable startup and runtime recovery. A launcher that works once, a live PID, or a tray icon is not a sufficient health signal.

## Goals

- Start the exact checkout at `C:\Dev\whisper-local` in the interactive user session after every login.
- Record bootstrap activity before Python or model initialization, so a missing launch can be distinguished from an application crash.
- Restart Whisper Local when its process exits unexpectedly.
- Recover a silent/dead audio callback without requiring the user to contact an assistant.
- Preserve the existing local model, NTNU routing, hotkeys, settings, transcript history, privacy boundary, and non-elevated input session.
- Avoid duplicate application or supervisor processes.
- Provide a checker that validates the actual installed mechanism and reports actionable failures.

## Non-goals

- Running Whisper Local as a Windows service or in a non-interactive session.
- Sending audio, health data, logs, or transcripts to any new remote system.
- Changing transcription models, cleanup prompts, language routing, or clipboard behavior.
- Claiming reliability without a real login/reboot and physical dictation acceptance test.

## Design

### 1. Interactive startup supervisor

A per-user Startup-folder entry launches a hidden PowerShell supervisor from the repository. The Startup folder is used instead of the registry `Run` value that failed the 2026-09-29 acceptance test. The obsolete `WhisperLocal` and `Whisper Local` registry values and the `\WhisperLocal` Scheduled Task remain absent, preventing competing instances and avoiding the previously observed non-interactive Task Scheduler behavior.

The supervisor:

- takes a named per-user mutex so only one supervisor runs;
- writes `%APPDATA%\whisperkey\supervisor.log` immediately on entry;
- launches `whisper-local-autostart.vbs`, preserving the existing CUDA-aware launcher chain;
- checks at a bounded interval whether the recorded application PID still belongs to the expected checkout;
- restarts a missing or exited application with bounded exponential backoff;
- never deletes or resets settings or transcript history; and
- rotates or bounds its local log so monitoring cannot grow without limit.

The Startup-folder entry is generated by `tools\repair-local-startup.ps1`. The repair is idempotent and uses the current repository path rather than embedding an unrelated interpreter or installation.

### 2. Application health and audio recovery

Whisper Local writes `%APPDATA%\whisperkey\health.json` atomically. The record identifies the application PID and timestamps for application heartbeat and the most recent audio callback. It contains no audio or transcript text.

The audio recorder tracks callback activity while its continuous input stream is expected to be active. If callback activity becomes stale, an internal monitor closes and reopens the selected input device. Recovery attempts are serialized so they cannot race recording start/stop. If a bounded number of reopen attempts fail, the application records the reason and exits; the external supervisor then starts a fresh process.

The supervisor treats a missing health record as normal during a generous startup grace period. After initialization, it restarts only when the expected process is absent or the application explicitly reports unrecoverable health. It does not kill a healthy process merely because model loading is slow.

### 3. Diagnostics and repair

`tools\repair-local-startup.ps1 -Check` validates all of the following:

- the Startup-folder launcher exists and targets this checkout's supervisor;
- both legacy registry startup values are absent;
- the obsolete Scheduled Task is absent; and
- the supervisor and application launch files exist.

The normal repair mode installs the exact Startup-folder launcher and removes obsolete startup registrations. Its output names the installed path and the local supervisor log. Static configuration success is reported separately from runtime health.

### 4. Safety boundaries

- Before terminating a process, the supervisor must verify both the PID and executable/command line point to `C:\Dev\whisper-local`.
- Restart attempts use backoff and a rolling failure limit to prevent a tight crash loop.
- All files are per-user and local under `%APPDATA%\whisperkey`; no administrator privileges are required.
- The NTNU API key remains only in the Windows environment variable and never appears in repository or health files.
- The current mutex in the application remains the final defense against duplicate application instances.

## Acceptance tests

Automated tests must cover launcher generation, exact-path validation, removal of obsolete registrations, supervisor single-instance behavior, missing-process restart, startup grace, backoff, stale/wrong PID safety, health-file atomicity, callback-staleness detection, successful stream reopen, and escalation to process exit after bounded failures.

The installation is not accepted until all of these manual tests pass:

1. Reboot Windows, log in, and confirm a new supervisor bootstrap entry and a new application initialization sequence without manually starting anything.
2. Dictate English with physical `Ctrl+Win` in a VS Code terminal and confirm automatic paste without right-click or `Ctrl+V`.
3. Dictate Norwegian and confirm Norwegian/Bokmål output rather than Swedish or another language.
4. Put the PC through sleep/Modern Standby, wake it, and repeat the physical dictation test.
5. Deliberately stop the application process, confirm the supervisor restarts it once, and repeat the physical dictation test.

Passing unit tests or observing a PID is not a substitute for these acceptance tests.
